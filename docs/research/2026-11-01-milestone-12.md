# Milestone 12: offline pinning — design

Date: 2026-11-01. rclone v1.75.2 still has no pinning in its VFS cache
(checked in `rclone help flags`), so the brief's design stands: pinning
lives in `nuage-fs`, the engine syncs the pinned items through rclone.

## Where an item lives

`nuage-fs` already sends every path to one of two places: the local-only
folder (excluded items) or the hidden rclone mount. Pinning adds a third:

```
~/Cloud/<account>/<path>
  excluded            → data/local-only/<account>/<path>
  pinned, in store    → data/pins/<account>/<path>      (full copies)
  anything else       → data/mounts/<account>/<path>    (rclone)
```

- A pinned path goes to the store **once its copy is there**. Until the
  first download ends it is still read through rclone, so pinning never
  makes a file disappear. New files created in a pinned folder go to the
  store at once.
- Listing a pinned folder (or a folder holding pinned files) merges rclone's
  listing with the store, the store winning. Items deleted locally but not
  yet deleted remotely are hidden (the engine gives `nuage-fs` the list).
- Pinning an excluded item is refused (it is not synced at all).

## Offline

The engine decides that an account is offline when the provider cannot be
reached (network errors of a cheap rc call, at the check interval), or
when its hidden mount cannot be mounted. `nuage-fs` is then told so:

- pinned items work as usual, from the store;
- everything else is listed from the metadata (the last listings the
  engine saved) and greyed in the browser; opening it fails at once with
  `EHOSTUNREACH`, so file managers do not hang;
- at start-up without network, `nuage-fs` is mounted even though rclone's
  mount fails; the engine retries the hidden mount and switches back when
  it works.

Tests simulate the network loss with `NUAGE_TEST_OFFLINE=<file>`: while
the file exists, the engine treats every account as offline (unmounts the
hidden mount, refuses remote calls).

## Metadata (SQLite, `rusqlite`, `data/pins.db`)

- `pins (account, path, kind, pinned_at)`
- `files (account, path, remote_size, remote_mtime, remote_hash,
  local_size, local_mtime, state)`: the reference state of each pinned
  file, i.e. what both sides looked like at the last sync.
- `listings (account, dir, entries)`: JSON listings of the pinned folders,
  of the parents of pinned items, and of every folder listed through the
  file commands, so that the tree stays navigable after an offline restart.

SQLite is compiled in (`bundled`): the static musl build needs `musl-gcc`
(`musl-tools`), its only C dependency.

## Sync (engine, every check interval and after a change)

For each file under a pin, with R the remote state (`operations/list`,
recursive, with hashes), L the store state and Ref the reference:

| Ref | Remote changed | Local changed | Action |
|---|---|---|---|
| none | present | absent | download |
| none | absent | present | upload |
| none | present | present | same content: record; else conflict |
| some | no | no | nothing |
| some | yes | no | download (or delete the local copy if deleted remotely) |
| some | no | yes | upload (or delete remotely if deleted locally) |
| some | yes | yes | conflict, unless one side deleted it: then keep the other |

- A conflict keeps both: the local version is renamed
  `name (conflict 2026-10-29 18-45).ext` and uploaded as a new file, the
  remote one is downloaded under the original name; a `PinStateChanged`
  event with `Conflict` makes a notification.
- Downloads go to a staging folder, then are renamed into the store
  (atomic for programs reading the file). Uploads use
  `operations/copyfile` from the store; files changed less than 3 s ago are
  left for the next round (still being written). A paused account does not
  upload.
- Hashes are compared when both sides have one, else size and date.
- Unpinning a file whose changes are not uploaded is refused without
  `force`; otherwise the copies and records are removed.

KeePassXC (and many editors) save by writing a temporary file and renaming
it over the original: inside a pinned folder both live in the store, and
for a pinned file the rename replaces the store copy. Both cases have a
test.
