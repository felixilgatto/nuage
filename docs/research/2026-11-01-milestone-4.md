# Milestone 4 findings (2026-11-01)

Ubuntu 26.04.1, fuse3 3.18.2, Flatpak 1.16.6, GNOME runtime 51, rclone v1.75.2, fuser 0.18.0.

## nuage-fs in the Flatpak (user installation)

Checked with `poc/flatpak-fuse/io.github.felixilgatto.NuagePoc.m4.yml`: `nuaged` in the sandbox, rclone and `nuage-fs`
mounting through `build-aux/flatpak/fusermount-wrapper.sh` and the static `nuage-fuse-relay`.

- `app-path` in `/.flatpak-info` is the host path of `/app`
  (`~/.local/share/flatpak/app/<id>/x86_64/master/<commit>/files` for `--user`); the host runs the relay from there.
  A system installation (`/var/lib/flatpak/...`) was not tested (needs root).
- Mounts made by the host's `fusermount3` **propagate into the sandbox**: `nuage-fs` in the sandbox reads the hidden
  rclone mount (`~/.var/app/<id>/data/mounts/<id>`, also visible at `/var/data/mounts/<id>`), and host processes read
  and write the user's folder (`fuse.nuage`). Writes from the host reached the source through both layers.
- `fuser`'s pure-Rust mount opens `/dev/fuse` itself and does not fall back to `fusermount3` when the device is
  missing: `nuage-fs` therefore mounts through `fusermount3` (`_FUSE_COMMFD`) and `Session::from_fd`.
- `Config::clone_fd` opens `/dev/fuse` for each thread: in the sandbox the serving threads died silently and every
  access hung (`request_wait_answer`). The threads now share one descriptor; a session error is logged.
- The relay must be static (`-C target-feature=+crt-static`): it runs on the host, whose glibc may be older than the
  runtime it was built against.

## Behaviour when rclone dies

- The hidden mount answers `ENOTCONN` / `ECONNABORTED` until it is detached. `nuage-fs` retries those while the
  daemon restarts rcd (detected within a second) and remounts; files open at that moment are reopened by path. A read
  started just before `kill -9` of rcd completes.
- rclone's `local` backend has no change notification: files created in the source folder behind rclone's back appear
  only when the directory cache expires (5 min).

## Performance of the relay (release build, `local` provider, same rclone VFS)

Seconds, direct access to the hidden rclone mount vs through `nuage-fs`:

| Case | Direct | nuage-fs |
|---|---|---|
| read 512 MB (first read) | 1.13 | 1.18 |
| read 512 MB again | 0.40 | 0.45 |
| write 512 MB + fsync | 0.54 | 0.71 |
| `ls -l`, 5000 files, first time | 0.16 | 0.24 |
| `ls -l`, 5000 files, again | 0.04 | 0.04 |
| create 1000 small files | 0.26 | 0.42 |

The cost is the second FUSE hop, about 0.1–0.2 ms per operation; `fuser` already negotiates the largest writes
(`max_write` 16 MB, `FUSE_MAX_PAGES`). Against Google Drive, each uncached operation costs a network round trip
(tens to hundreds of milliseconds), so the difference should not be noticeable. The kernel write-back cache, which
would hide part of it, is left off: it changes write ordering and mtime semantics.
